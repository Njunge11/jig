# Skill evals — report, 2026-09-19

## Verdict

The skills work.

- Delivery: all 5 lane agents hold the rules in context. 5 of 5 cases pass.
- Obedience: 28 of 28 cases pass with the plugin, after a hand check of each judge FAIL. With no plugin, Sonnet passes 3 of 28.
- Triggering: 9 of 9 cases pass, with one known weakness (see section C).
- The run found 5 defects in skill text. All 5 are fixed and proved by a rerun.

## Method

- Tool: `claude plugin eval`, Claude Code 2.1.278. Each case runs with the plugin and with no plugin. Δ is the score difference.
- Model under test: Sonnet. Suite: 42 cases in `plugins/jig/evals/`; `docs/evals/checklist.md` says what each case proves.
- Judge: the full B run used the default small judge; each case with a FAIL ran again with a Sonnet judge. The A and C cases use no judge.
- Each rule clause has its own grader, so a failure names the clause. Each clause quotes skill text; I checked each quoted phrase against the `SKILL.md` files.
- Each FAIL of a with-plugin run was checked by hand against the answer text.
- Cost that the harness reports, all runs of the day: $34.11 at list price.

## C. Triggering

9 of 9 pass: on 7 natural prompts Sonnet loaded the correct skill, and on a git prompt and a regex prompt it loaded none.

Known weakness: the skeleton-bug prompt loaded the skill in 1 of 2 runs. When the skill did not load, Sonnet gave the wrong fix (`keepPreviousData`). A main session can miss a skill. A lane agent cannot, because it preloads each skill. Run builds through `implement-frontend` and `implement-backend`.

## What the first pass got wrong

- The first graders were one rubric of 5 or 6 clauses per case. The judge failed correct answers and gave no reason. The official doc says the same: an `llm` grader "differs more the longer the text it has to read", and "suspect the judge before the plugin". One grader per clause fixed it.
- The default small judge gave 10 wrong FAIL votes on 15 checked clauses. `--judge-model sonnet` is now the documented run command.
- Four grader clauses were my faults: two demanded literal names that the skill's own example does not use (`b10`), one demanded a rule that belongs to another skill (`b14`), one demanded copy that the spec does not give (`b17`).

## Not proved

- Most cases ran one time. `b11`, `b17` and `b28` ran 2 or 3 times. A one-run score is one sample.
- Sonnet only. Haiku and Opus were not run.
- The FAIL votes of the no-plugin arm were not checked by hand. If the judge is too strict there, the true Δ is smaller.
- `implement-*` and `review-*` have no case. They fork a lane agent and need a repository with a diff, and the eval harness gives read-only tools unless a scaffold script runs.
- The A cases tell the subagent to use no tool; the harness does not keep the subagent trace to confirm it.
- The code samples inside the recipes are not run by these evals. An agent that copies a sample passes a clause that quotes the sample. Only a test that runs the sample proves the sample.
