# Sources

Every rule in `SKILL.md` comes from one page of the XState v5 docs at `https://stately.ai/docs/<page>`. The table quotes the line that grounds the rule. When a quote and the live page disagree, the live page wins. Report the drift.

The docs were read in full on 2026-09-14 against `xstate` 5.33.0 and the `@xstate/react` page of the same docs.

## Rule to source

| Rule | Page | Quote |
| --- | --- | --- |
| Finite state and context make up the state | `finite-states` | "You can combine finite states with context, which make up the overall state of a machine". |
| An event causes a transition; a transition names the target | `transitions` | "An **event** is a signal, trigger, or message that causes a transition." "A **transition** is a change from one finite state to another, triggered by an event." |
| A tag groups states, such as `loading` | `tags` | "you can signify which state nodes represent states in which data is being loaded by using a 'loading' tag". |
| Start flat and small | `finite-states` | "Start simple and shallow": "Begin with minimal states: Don't create multiple finite states until it becomes apparent that the behavior of your logic differs depending on some finite state it can be in." "Prefer flat structures initially". |
| Nest only for shared transitions | `parent-states` | "Start Flat, Then Nest": "Begin with a flat state structure and only introduce parent states when patterns emerge". "Common Patterns for Parent States": "Shared Transitions", "Common Entry/Exit: If multiple states share entry or exit actions, they might belong in the same parent state". "Keep the hierarchy as shallow as possible". |
| Different behavior is a different state | `finite-states` | "Different behavior = different state: Create separate states when the application behaves differently in response to the same event." "Same behavior = same state: If multiple 'states' handle events identically, they should probably be a single state." |
| Name in domain words | `finite-states` | "Name states clearly": the examples contrast `signedOut`, `signingIn`, `authenticationFailed` with `state1`, `state2`, `error`. |
| Model the workflow with loading and error states | `finite-states` | "Model user workflows": the example carries `idle`, `validating`, `submitting`, `success`, `error`. |
| Parallel regions stay independent | `parallel-states` | "Avoid transitions between regions: Each region in a parallel state should be independent and not directly transition to states in other regions." |
| Top-level final terminates; no exit actions | `final-states`, `actions` | "Top-level final states": the actor stops. `actions` § "Entry and exit actions": "Top-level final states cannot have exit actions, since the machine is stopped and no further transitions can occur." |
| Child final marks the parent done | `final-states` | "Child final states": the parent's `onDone` transition is taken. |
| Create with `setup` and types | `setup`, `typescript`, `output`, `event-emitter` | "More robust machine logic, as named sources are guaranteed to exist"; "Better type inference for actions, actors, guards, delays, context, events, etc." `typescript` § "Specifying types": "The recommended way to strongly type your machine is to use the setup(...) function". `output` and `event-emitter` show `output: {} as ...` and `emitted: {} as ...` in `setup({ types })`. `typescript` § "Specifying types": types go in `setup({ types })`. `tags` § "Tags and TypeScript": tags typed in `setup`. |
| Reference actions and guards as objects, not inline functions | `actions`, `guards` | "Inline actions are useful for prototyping and simple cases but we generally recommended using action objects." `guards` § "Inline guards": "This is useful for quickly prototyping logic but we generally recommended using serialized guards". `typescript` § "Dynamic parameters": "It is recommended to use dynamic parameters in actions and guards as they allow you to make reusable functions that are not closely tied to the machine, and are strongly-typed." |
| `assertEvent` only when params are infeasible | `typescript` | "Asserting events": "It is strongly recommended to use dynamic parameters instead of directly accessing the event object whenever possible for improved type safety and reusability." "If using dynamic parameters is infeasible... you can assert the event type using the assertEvent(...) helper function." |
| Full transition object over string shorthand | `transitions` | "Shorthands": "Using the string target shorthand is useful for quickly prototyping state machines. Generally, we recommended using the full transition object syntax as it will be consistent with all other transition objects." |
| `createStateConfig` and type-bound helpers | `machines` | "Modularizing states" (Since 5.21.0): "useful for very large, complex state machines". "Type-bound action helpers" (Since 5.22.0): "Can be defined in any file that imports the machineSetup". `setup` § "Extending setup" (Since 5.24.0). |
| Static state data lives in `meta` | `finite-states` | "Meta": "Meta data is static data that describes relevant properties of a state node... This can be useful for displaying information about a state node in a UI, or for generating documentation." |
| `description` documents a state | `finite-states` | "Document state purpose": "Use descriptions: Add .description properties to explain complex states." "Include meta data: Store relevant information about what each state represents." `states` § "State descriptions". |
| A group of states is a tag | `tags` | "State nodes can have tags, which are string terms that help group or categorize the state node." `finite-states` § "Group related functionality": "Use tags for categorization: Group states by common characteristics." |
| Read state data from the snapshot | `states` | "state.getMeta()": "It is an object with keys that represent the state node IDs, and values that are the metadata of that state node." "state.hasTag(tag)", "state.matches(stateValue)". "state.can(eventType)": "The state.can(...) method will also check transition guards by executing them." "mapState(snapshot, mapper)" (Since 5.31.0): "maps a machine snapshot's active state nodes to values using a hierarchical mapper object"; "The mapper mirrors the state hierarchy of the machine."; "mapState is fully typed: state keys are validated against the machine's state hierarchy". |
| `getNextTransitions` lists the available events | `machines` | "Next transitions" (Since 5.26.0): "useful for introspecting what events a state machine actor can respond to in its current state"; use cases include "Building UIs that show available actions". |
| Prefer `hasTag` over `matches` | `states` | "Prefer using state.hasTag(tag) over state.matches(stateValue), as state.hasTag(tag) is more resilient to changes in the machine." |
| No string-keyed table beside the machine | `states` | "mapState is fully typed: state keys are validated against the machine's state hierarchy, and the snapshot type is inferred in map functions." A table outside the machine gets no such validation, and `hasTag` exists because state names change. |
| Guards are pure and synchronous | `guards` | "Guards should be pure, synchronous functions that return either true or false." `and`, `or`, `not` under "Higher-level guards". "stateIn... is most useful for parallel states". |
| Targetless transition to run actions | `transitions` | "A common mistake is using target: 'process' on a parent state transition when you only want to execute actions. This will re-resolve child states to their initial state. To preserve child states, omit target entirely." "Re-entering": "Re-entering (target + reenter: true)... Re-executed... Restarted". |
| Context is immutable, `assign` changes it | `context` | "The context object is immutable, so you cannot directly modify it. Instead... you can use the assign(...) action to update context." |
| Context is serializable | `persistence` | "Caveats": "the state must be serializable, which means that it must be JSON-serializable". |
| `input` over a factory function | `input` | "Use-cases": "Replaces the old way of writing a factory function for machines". |
| Built-in actions return objects | `actions` | "Built-in actions, such as assign(…), sendTo(…), and raise(…), are not imperative; they return a special action object... Do not call built-in action in custom action functions." "Imperative built-in actions are available in enqueueActions(…)". |
| `always` needs guard or target | `eventless-transitions` | "Eventless transitions with no target nor guard will cause an infinite loop." "Observability and transient states": a state entered and left in one step never appears in `subscribe()`, `waitFor()`, `matches()`, `hasTag()`; use `after: { 0: '...' }` when it must be observed. |
| Named delays | `delayed-transitions` | "Referenced delays": "define referenced delays by specifying a string delay key, and providing the actual delay time separately" in `setup({ delays })`. |
| `raise`, `sendTo`, `emit`; no `sendParent` | `actions` | "Raise action": "raises an event that is received by the same machine". "Send-to action". "Send-parent action": "Prefer sendTo(...): pass actor refs (such as the parent actor ref) to other actors via input or events". `event-emitter` (Since 5.9.0). |
| Wildcard as catch-all, throw for strict | `transitions` | "Wildcard transitions". `migration` § "Use wildcard * transitions, not strict mode": "Strict mode is removed. If you want to throw on unhandled events, you should use a wildcard transition". |
| Async work is an invoked actor | `invoke` | "How are actors different from actions?": "Actions are 'fire-and-forget'... If you specify an action as async, the action won't be awaited before moving to the next state." |
| Invoke a known set, spawn a dynamic set | `actors` | "Invoking and spawning actors": "a loadTodos actor would be an invoked actor; it represents a single state-based task. In comparison, each of the todos can themselves be spawned actors, and there can be a dynamic number". `spawn`: "In most cases, prefer spawnChild"; "Best Practices" covers cleaning refs from context. |
| Actor logic under `setup({ actors })` | `invoke` | "Source": "The src represents the actor logic". `migration` § "Use actor logic creators for invoke.src instead of functions". |
| The machine module holds the logic; implementations default in `setup` and override through `machine.provide` | `setup`, `migration` | `setup`: "named sources are guaranteed to exist". `machines` § "Providing implementations": "Machine implementations are the language-specific code that is executed but is not directly related to the state machine's logic (states and transitions)." "The default implementations can be provided in a setup({...}) function"; "You can override default implementations by providing implementations via machine.provide(...)". `pure-transitions` § "Actions": custom actions "won't execute in pure functions", so the backend runs them itself; `xstate-react` § "useMachine": the client passes `machine.provide(...)` to the hook. |
| Pure transitions on the server, without a live actor | `pure-transitions` | "Pure transition functions allow you to compute the next state and actions of a state machine without creating a live actor or executing any side effects. This is useful for server-side applications". |
| Persist to the database; restore with the `snapshot` option | `persistence`, `xstate-react` | `persistence`: "storing the state of an actor in persistent storage, such as localStorage or a database". `xstate-react` § "Persisted and rehydrated State": "You can persist and rehydrate state with useMachine(...) via options.snapshot". |
| Pure `transition` on the server | `pure-transitions` | "Server-friendly: Perfect for server-side workflows and API endpoints". `transitions` § "Determining the next state": "It is recommended to use the initialTransition(…) and transition(…) functions instead of getNextSnapshot(…) and getInitialSnapshot(…), which will be deprecated." |
| Caller runs the returned actions | `pure-transitions` | "Actions": actions come back in the tuple and are not executed; custom actions are `{ type, params }` objects. |
| Persist and `resolveState` | `pure-transitions` | "Resolving Persisted State": `const restoredState = machine.resolveState(JSON.parse(stateToPersist));` then `const [nextState, actions] = transition(machine, restoredState, event);`. `persistence` § "Persisting state machine values": "you can use the machine.resolveState(...) method", with `{ value: restoredStateValue, // context: { ... } }`. |
| Live actor restores with `snapshot` | `persistence` | "Restoring state": `createActor(feedbackMachine, { snapshot: restoredState });` then `feedbackActor.start();`. "Actions from machine actors will not be re-executed, because they are assumed to have been already executed. However, invocations will be restarted, and spawned actors will be restored recursively." "Deep persistence". |
| Snapshot is JSON; caveats; event sourcing | `persistence` | "Caveats": "Replaying actions: actions that have already been executed will not be re-executed. Event sourcing is preferred for this use-case." Serialization and incompatible-state caveats in the same list. "Event sourcing": "persist the events as they happen using the inspection API, and then replay them". |
| `getMicrosteps` | `pure-transitions` | "Microsteps": "each microstep is a [snapshot, actions] tuple representing an intermediate state and its associated actions". |

| Branch the view on `matches`, prefer `hasTag` | `xstate-react`, `states` | "Matching states": "When using hierarchical and parallel machines, the state values will be objects, not strings. In this case, it is best to use state.matches(...)." | Restore in React with `snapshot` | `xstate-react` | "Persisted and rehydrated State": "You can persist and rehydrate state with useMachine(...) via options.snapshot". `persistence`: "storing the state of an actor in persistent storage, such as localStorage or a database". |
| `machine.provide` as the first argument | `xstate-react` | "useMachine" example: "Machine with provided implementations.
